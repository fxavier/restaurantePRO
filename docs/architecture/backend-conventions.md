# Backend conventions

Owner: `software-architect`. Sources: [product_description.md](../product_description.md) (§6, §7, §9, §10, §12), [backend-decisions.md](../design/backend-decisions.md) (D1–D33), [r2-decisions.md](../design/r2-decisions.md) (D34–D63), the [ADRs](../adr/README.md), [PRD R1](../prd/r1-foundation-stage1.md), [PRD R2](../prd/r2-stage2.md). Each rule names the test that enforces it. A rule without a test is a wish.

## Modules

- One module per direct subpackage of `com.xavier.backend`. Every module has a `package-info.java` with `@ApplicationModule(allowedDependencies = {...})` following D13. Name only modules that already exist: Modulith rejects an unknown name. **Enforced by** `ModularityTests.modulesRespectTheirDeclaredBoundaries`. The `ModularityTests.anIllegalModuleDependencyIsDetected` test proves that verify fails.
- `shared` is `Type.OPEN`. It holds only technical types (D14) and depends on nothing.
- `access` holds the authorization primitives `com.xavier.backend.access.Permission`, `com.xavier.backend.access.Actor` and `com.xavier.backend.access.AccessPolicy` (D13 amendment, S0b). It depends only on `shared`, and its root types are public API for every module, so `organization` and `identity` can both use it without a cycle.
- `audit` depends on `shared` and `access` (D35): it reads the current actor for `recordAsCurrentActor` (D41).
- `config` holds the security filter chains, the correlation-id filter, session and scheduling configuration and the POS change stream (`NotificationController`). Nothing depends on it.
- Public API is the module's **root package** plus any `@NamedInterface` (`model/dto`, `model/event`, a `<Module>Api` facade). Entities, repositories, services and controllers stay in subpackages and are internal (D12).
- Facades (D36) are one per consumer concern (`DiningApi`, `CatalogApi`, `OrdersApi`, `OrdersProductionApi`, `CashApi`, `FiscalApi`). Their writes are `@Transactional(propagation = MANDATORY)`, so the coordinator (settlement) composes them in its own transaction, and they never authorize: the calling use case already did. For a resource addressed by id a facade offers a scalar store read (`OrdersApi.storeOf(orderId)`, `CashApi.storeOfDay(dayId)`, 404 when absent), so the caller authorizes on it (D42 (b)) before it takes any lock or loads anything (D51: the first lock belongs to an authorized use case). Coordinated closes (order, document, session, day) live in `settlement` (D37).
- Module docs (D44): `ModularityTests.generatesModuleDocumentation` writes them to `backend/target/modulith-docs/` on every run and asserts each file exists. Only `rtk mvn test -Dtest=ModularityTests -Dmodulith.docs=true` writes the committed [modules/](modules/), and only the integration slice runs and commits that (the Documenter's output order is not deterministic). Slices never commit `docs/architecture/modules/`.

Module layout (D12): `model/`, `model/dto/`, `model/event/`, `repository/`, `service/`, `controller/`, `exception/`, `adapter/` (implementations of the module's outbound ports, e.g. `production/adapter` for the ESC/POS printer transport). Create a package only when it has content. The port interface stays where its callers see it (the module root when another module or a test supplies it, such as `settlement.PaymentProvider`); future payment-provider adapters (D53) go in `settlement/adapter/`, and existing packages are not moved.

## Layer rules (ArchUnit, `ArchitectureTests`; `ArchitectureRulesFireTest` proves each rule fires)

| Rule | Test |
|---|---|
| Controllers never depend on repositories or entities | `controllersDoNotTouchRepositoriesOrEntities` |
| Repositories (`..repository..`, `@Repository`, Spring Data) are used only by services (`..service..` or `@Service`) | `repositoriesAreUsedOnlyByServices` |
| `dto`/`event` packages never contain or reference `@Entity`/`@Embeddable` | `entitiesStayOutOfDtosAndEvents` |
| No `double`/`float` fields anywhere, none returned from `model` (use `Money`/`BigDecimal`, D15) | `noFloatingPointFields`, `noFloatingPointInModelSignatures` |
| No zero-arg `Instant.now()`/`LocalDate.now()`/...: inject `Clock` (D16) | `timeComesFromTheClock` |
| Constructor injection only (no `@Autowired` fields) | `noFieldInjection` |
| `model/event` types are records | `eventsAreRecords` |
| No `ErrorResponseException` subtypes (coded errors extend the shared exceptions; only `identity.LoginThrottledException`, a 429, is exempt) | `codedErrorsUseTheSharedExceptions` |
| D35 forbidden edges: `orders` ↛ `settlement`, `production`; `cash` ↛ `orders`, `settlement`; no module → `production` (`verify()` alone accepts them once a `package-info` allows them) | `forbiddenModuleDependenciesAreAbsent` |

## Shared contracts (S0)

- **Money**: `com.xavier.backend.shared.Money(BigDecimal amount, Currency currency)`. Construction never rounds and rejects excess decimals. `times(BigDecimal)` and `divide(BigDecimal)` are the only rounding points (HALF_UP to the minor unit; D59: `net = gross.divide(1 + rate/100)`, a zero divisor throws). `allocate(int)` and `allocate(List<BigDecimal>)` use largest remainder, so the parts always sum to the total. Mixing currencies throws `IllegalArgumentException`. Tested by `MoneyTest`.
- **Errors** (`shared.exception`): extend `NotFoundException` (404), `ConflictException` (409) or `BusinessRuleException` (422), one subclass per business meaning. A stale `@Version` (`OptimisticLockingFailureException`) gives 409. Bean Validation gives 400 with `errors: [{field, message}]`. `AccessDeniedException` gives 403 and `AuthenticationException` gives 401. Anything else gives 500 with no internal detail. Every error body is an RFC 9457 `ProblemDetail`. Tested by `GlobalExceptionHandlerTest` and `SecurityConfigTest`.
  - **Coded errors** (S7b, PRD R2 conventions): every R2 business-rule 422 and state 409 carries a stable `code` property that clients switch on; a code is never renamed once released. Pass it to the shared constructor: `new BusinessRuleException(String code, String message)`, `(code, message, Map<String, ?> properties)` and `(code, message, properties, Throwable cause)`; the same four on `ConflictException`; `NotFoundException(code, message[, properties])`. The handler renders `detail` = message, `code` (omitted when null: the one-argument R1 constructors stay uncoded) and each property (e.g. fiscal's `documentId`, catalog's `errors` list). Properties must not shadow `code`, `type`, `title`, `status`, `detail` or `instance` (`IllegalArgumentException`). Module subclasses expose `code()` and `properties()` from the sealed base `shared.exception.CodedException`; keep a typed accessor where callers need one (e.g. `CashRuleViolationException.rule()`). Tested by `GlobalExceptionHandlerTest`, `CodedExceptionTest` and `architecture.CodedErrorContractTest` (strict body: status, title, detail, instance, code, every extra property). Add a case there when you release a new code or property.
  - Do not subclass Spring's `ErrorResponseException` (ArchUnit `codedErrorsUseTheSharedExceptions`). The only exception is `identity.LoginThrottledException`: a 429 with `Retry-After` is neither a business rule nor a conflict.
- **Time**: inject `java.time.Clock` (UTC). The bean ticks in whole microseconds (`Clock.tick(Clock.systemUTC(), Duration.ofNanos(1000))`), because PostgreSQL `timestamptz` stores microseconds: an instant with nanoseconds differs from itself after a round trip (`ClockConfigurationTest`). Tests pin it with a `@TestConfiguration` that declares a `@Primary Clock`; keep a test clock microsecond-precise too.
- **Pagination**: accept a `Pageable` and return `PageResponse.from(page)`. Size is capped at 200 (`PageResponseTest`).
- **Idempotency** (D24, D47, D63): controllers of repeatable commands inject `access.IdempotentRequests` and return
  `idempotent.execute("<module>.<operation>", key, request, body, ResponseType.class, () -> ResponseEntity...)` (or `idempotent.steps(...)` for a command with an external-call step, D63), with `key` from `@RequestHeader("Idempotency-Key")`. It derives the scope `"<op>:<kind>:<principalId>"` (D38) from the current actor and the target `request.getMethod() + " " + request.getRequestURI()`, then calls `shared.idempotency.IdempotencyService.execute(String scope, String key, String target, Object body, Class<T> type, Supplier<ResponseEntity<T>> action)` (or `executeSteps`). It lives in `access` because the scope needs the `Actor` and `shared` depends on no module; do not write a module-local copy. Call it from the controller, outside any transaction: called inside one it throws `IllegalStateException` before claiming the key. The request identity is the SHA-256 of `target` plus the canonical JSON body. Approver code and PIN travel in the `X-Approver-Code`/`X-Approver-Pin` headers and are never part of the body (D40).
  - Same key and same target+body → the stored status, `Location` header and body are replayed; the body is deserialized into `T` (a `String` comes back as itself).
  - Same key with a different target or body → 422.
  - A duplicate while another request holds the key → 409. Only SQLSTATE 55P03 (lock_not_available) means that; a deadlock (40P01) or serialization failure (40001) propagates.
  - A missing, blank or over-255-character key → 400.
  - Only 2xx is stored (D47.3): business errors are **thrown**, which rolls back the action, so a retry with the same key evaluates the rule again. An action that returns a non-2xx `ResponseEntity` is a programming error (`IllegalStateException`, nothing stored).
  - Crash-safe: the action runs only while holding the record's row lock (`FOR UPDATE NOWAIT`), and its effects and the stored response commit together. After a crash or a failed action, the next request with that key takes the claim over and runs it once. The action's transaction is `READ COMMITTED`; take explicit short locks when you need more (D47.5).
  - Retention (D47.4): `IdempotencyRetention` deletes, daily at `restaurantpro.idempotency.retention-cron`, `COMPLETED` records whose `completed_at` and abandoned `IN_PROGRESS` claims (left by a crash or a refused action) whose `created_at` are older than `restaurantpro.idempotency.retention` (default `P90D`). A claim whose step lease is still live is kept.
  - Multi-step commands (D63): a command whose steps must run with no transaction, because one of them calls an external system (`FiscalApi.issue`, `provider.status`), uses `<T> ResponseEntity<T> executeSteps(String scope, String key, String target, Object body, Class<T> type, Supplier<ResponseEntity<T>> steps)` instead. It is called the same way, from the controller, and keeps the same hash, 422, replay, `Location` and 2xx-only rules.
    - The key is claimed with a lease (`lease_owner`, `lease_until` = now + `restaurantpro.idempotency.step-lease`, default `PT30S`). A live lease gives 409. An expired lease is taken over by compare-and-set, so only one of several concurrent retries wins.
    - The steps run with no transaction bound and no lock on the record. `ExternalCalls.requireNoTransaction()` is checked on entry and again after the steps return. Each step opens its own short transaction, so a request holds at most one connection at a time. **Every step must be idempotent by domain state**: the lease only suppresses duplicate work.
    - Only the lease owner can complete. If the lease was lost and the taker already stored its response, that response is replayed.
    - A thrown exception, or a non-2xx response (`IllegalStateException`), expires the lease and stores nothing. A retry with the same key then runs the steps again immediately. After a crash, the lease expires on its own.
    - **Each operation scope uses exactly one mode.** Use `execute` unless a step makes an external call. `executeSteps` refuses an unfinished claim made by `execute` (`IllegalStateException`). `execute` does not check for leases, so never mix the two modes within one scope (`IdempotencyStepsTest`).
  - Never write your own (`IdempotencyServiceTest`).
- **External calls** (D48): the action of `execute` runs in a DB transaction, so it never calls an external system. Payment provider and remote fiscal calls use "persist, then call, then record": the domain row (e.g. a `PaymentAttempt` in `CREATED`) is the claim, a compare-and-set moves it to `PENDING` so exactly one submitter calls, the call runs with no transaction or lock, and a second transaction records the outcome (`UNKNOWN` on timeout). Every adapter's first line is `ExternalCalls.requireNoTransaction()`, which throws `IllegalStateException` when a transaction is active or a connection/`EntityManager` is bound to the thread (`ExternalCallsTest`).
- **Persistence helpers** (D43): `shared.persistence.UniqueConstraints.saveAndFlush(repository, entity, () -> new XTakenException(...), "x_uk", ...)` turns a violated named unique constraint (also one lost in a race) into its 409 exception; `UniqueConstraints.isViolated(e, names...)` for the rare multi-branch case. `shared.persistence.OptimisticLocking.requireVersion(Type.class, id, stored, sentByClient)` gives 409 for a stale client version. Never copy them into a module (`UniqueConstraintsTest`; each module's race tests).
- **Change notices** (D60): a use case that changes what a POS screen shows calls `changeNotifier.notifyAfterCommit(storeId, ChangeTopic.X, id)` inside its transaction (`IllegalStateException` outside one). Clients on `GET /api/v1/pos/notifications` (`text/event-stream`, store from the session, `DINING_VIEW` or `PRODUCTION_VIEW`) receive `{topic, id}` after the commit, nothing after a rollback, and never data: they re-read through the authorized GET. Topics: `TABLES`, `ORDER`, `CATALOG`, `PRINT_JOBS`, `PAYMENT_ATTEMPT`. In memory, no replay, 25 s heartbeat, 30 min emitter timeout (`SseNotificationTest`). Notices and heartbeats are written by the notifier's single sender thread, never by the committing or scheduler thread; a timed-out emitter is completed, so the client simply reconnects (`ChangeNotifierStreamTest`).
- **Scheduling** (D46): `@EnableScheduling` is on (`config.SchedulingConfig`). One backend per installation; jobs must stay correct under overlap (`SKIP LOCKED`, compare-and-set updates). Put a job in a `@Service` (repositories are used only from services).
- **Audit** (D20, D41): inside the use case's `@Transactional` method call `auditLog.recordAsCurrentActor(action, entityType, entityId, storeId, approverId, reason, details)`: actor id, actor kind and terminal come from the session. A write nobody asked for in a session (bootstrap, scheduled job, listener, device enrolment) uses `auditLog.recordAsSystem(action, entityType, entityId, storeId, terminalId, reason, details)` (`actor_kind = SYSTEM`, no actor). `recordAs(actor, ...)` is only for login and logout. All require an existing transaction (`MANDATORY`). There is no hand-filled `AuditEntry` path. `audit_event.terminal_id` is where the actor acted, not the entity (the entity is `entity_type`/`entity_id`). Details carry no PIN, password, token or card data, and keys that look like secrets are rejected. The secret-key guard checks top-level keys only. The database refuses UPDATE, DELETE and TRUNCATE on `audit.audit_event`, a `SYSTEM` row that names an actor, and an `ACCOUNT`/`EMPLOYEE` row without one (`AuditLogTest`).
- **Authorization** (D27): the first line of every BackOffice use case is `accessPolicy.require(Permission.X, storeId)` (or `require(Permission.X)` for installation-wide operations). Controllers never authorize. Authorities are `PERM_X` (all stores) and `PERM_X@<storeId>`. `Actor.authorities()` is the only source for these decisions; login builds the `Authentication`'s granted authorities from the same set (actuator URL rules read those). Denials are logged at WARN (`AccessPolicyTest`, `SecurityConfigTest`). `Permission` is append-only; a new constant needs a migration that grants it to the administrator role (`RoleSeedTest`).
- **Actor** (D38): `Actor(ActorKind kind, UUID userId, UUID employeeId, UUID terminalId, UUID storeId, Set<String> authorities)`. `userId` is the principal id: the account for `ACCOUNT`, the employee for `EMPLOYEE` (then equal to `employeeId`; an `ACCOUNT` has no `employeeId`). Build it with `Actor.account(...)` / `Actor.employee(...)`. Business facts store typed columns, never the bare `userId`: POS facts `*_employee_id`, BackOffice facts `*_account_id`. Changing `Actor`'s shape invalidates stored sessions: a stored attribute this release cannot read is treated as absent (`config.SessionConfig`), so the user gets 401 and logs in again (`OutdatedSessionTest`). Note that a record's `serialVersionUID` is not checked by Java serialization; the canonical constructor's checks are what reject an old shape.
- **POS context** (D39, D45): every POS use case starts with `PosContext pos = accessPolicy.requirePos(Permission.X)` (or `requirePosAny(...)`) and takes `pos.employeeId()`, `pos.terminalId()`, `pos.storeId()` from it. POS write endpoints never take a store or terminal from the request. `requirePos` gives 403 unless the actor is an `EMPLOYEE` with a terminal, holds the permission in the session's store, and that store is active (`access.StoreActivity`, implemented by `organization`, cached per request). A BackOffice session calling a POS write gets 403 (`AccessPolicyTest`). Only `access.AccessPolicy` reads the security context: code that runs both in and out of a session (an audit that records the current actor or the system) asks `accessPolicy.currentIfPresent()` (`Optional<Actor>`), never `SecurityContextHolder`, and never for an authorization decision.
  - A POS read that accepts an optional `?storeId=` calls `accessPolicy.requirePos(Permission.X, requestedStoreId)`: `null` means the session's store, another store gives 403 (logged). For a resource addressed by id, after `requirePos(Permission.X)` and the 404 read of its `storeId`, call `accessPolicy.requireSessionStore(pos, resourceStoreId, ENTITY, id)`: 403 when it is another store, and the denial log names the resource.
- **Approvals** (D40, D28): an approved command runs in two phases. The controller first calls the service's non-transactional `authorize...(id, approverCode, approverPin)`, which calls `ApproverVerifier.verify` and returns the module's `service.Approval` record; then `idempotency.execute(...)` runs the transactional apply with it. Never verify an approver inside the use-case transaction (a second connection, and the order lock held for the BCrypt time). The approver must not be the operator (422 `SELF_APPROVAL`).
- **Any of several permissions** in a store (BackOffice): `accessPolicy.requireAny(storeId, Permission.A, Permission.B)` passes when any one is held installation-wide or `@storeId`, and logs one denial naming all of them. Never test `actor.authorities()` by hand.
- **Store-scope check order** (D42): (a) when the store is an input (the POS session, or a `storeId` in the body or query), call `require`/`requirePos` before any read; (b) for a resource addressed by id, read only its `storeId` (404 if the row is absent), then `require` (403). Never load fully, then authorize. Every module adds a test for both orders (R2 slices; R1 modules follow when touched).

## Persistence

- Flyway, one history, `db/migration/<module>/V<block>__<module>_<what>.sql` with blocks shared/audit 1xxx, organization 2xxx, identity 3xxx, dining 4xxx, catalog 5xxx (D5), orders 6xxx, production 7xxx, cash 8xxx, settlement 9xxx, fiscal 10xxx (D61). Existing modules use the next free number in their own block. Never edit an applied migration.
- One schema per module (`CREATE SCHEMA IF NOT EXISTS <module>`), with no cross-module foreign keys (D6). Constraints back every invariant they can express.
- `spring.jpa.hibernate.ddl-auto=validate`: entities must match the migrations, and every context start checks it.
- UUIDv7 ids: `@UuidGenerator(style = VERSION_7)`.
- **Locks** (D17, D51). Human edits use `@Version` (409). Short pessimistic locks only where the decisions name them, always in this order within a transaction, and never held across a call that leaves the JVM:
  - settlement: `order_settlement` (`SettlementLocks`, the first lock of every pay, issue or close) → `cash_session` / `cash_day` → fiscal (`fiscal_document` before `fiscal_series`).
  - orders: claim an order by moving its version first (`OrderLookup.claim`); several orders are claimed in ascending id order (transfers, merge). A table opening or move writes the order row (and its open-table unique entry) first, then calls `DiningApi` (occupation and table `FOR UPDATE`).
  - dining: table, then area (`DiningRows`).
  - **Decide on the locked row.** A locking JPQL query on an entity the transaction already manages takes the lock but returns the stale instance. Lock with `find` + `refresh(entity, lockMode)` (`cash.service.RowLocks`, `dining.service.DiningRows`), or a compare-and-set `UPDATE … WHERE status = ?` with a row-count check (`PaymentAttemptRepository.markSubmitted`).

## Events

- Cross-module events go through the Spring Modulith JPA publication registry (`event_publication`, D19). Listeners use `@ApplicationModuleListener` and must be idempotent.
- `spring.modulith.events.republish-outstanding-events-on-restart=true`: when the application starts, it delivers again every publication whose listener had not completed. This is safe because each installation runs one instance. `EventRepublicationTest` proves it with a real second application context started on the same database.

## Web and security

- Routes: `/api/v1/auth/**` (open), `/api/v1/pos/**`, `/api/v1/backoffice/**` (authenticated session). POS and BackOffice call the same service.
- CSRF uses the SPA pattern. A `GET` sets the readable `XSRF-TOKEN` cookie, and mutating requests send it back in `X-XSRF-TOKEN`. In MockMvc tests use `.with(csrf())`, or send the cookie and header as `SecurityConfigTest` does.
- Sessions are stored in PostgreSQL (`shared.spring_session`). The cookie is `Secure; HttpOnly; SameSite=Lax`, and Boot applies this only on a real server (`WebServerSecurityTest`).
- Actuator runs on the management port (8081 by default). `health` is open. Every other endpoint needs `PERM_SYSTEM_MONITOR`.
- `ASYNC` and `ERROR` dispatches are permitted (the original request was authorized; the SSE stream completes on an async dispatch).
- The Hikari pool holds 20 connections (D40: 10 terminals; approver verification commits on its own connection before the use case's transaction).
- Every response carries `X-Correlation-Id`, and every JSON (ECS) log line carries `correlationId` (`CorrelationIdTest`).

## Tests

- Real PostgreSQL only: `@Import(TestcontainersConfiguration.class)`. One `postgres:18.6-alpine` container serves the whole JVM. Tests share the database, so use fresh UUIDs and keys per test and never assume empty tables.
- Draw per-test ids and keys in `@BeforeEach` or in the test method, never in a field initializer: in module tests one test instance has been seen serving all of a class's methods, so a field-initialized id leaks between them (`81ec2c1`, `TerminalAndVoidTicketsTest`).
- No JUnit `@Nested` test classes. Surefire's plain-text reporter misattributes a class with a nested container (its `.txt` shows 0 tests), which breaks the per-class evidence. Use another top-level class.
- The gate is `cd backend && rtk mvn clean test`: BUILD SUCCESS with 0 failures, 0 errors and **0 skipped**. No `@Disabled`, no assumptions that skip; stream only the cases that apply (`@MethodSource`).
- Module tests: `@ApplicationModuleTest(extraIncludes = {"shared", "access", "audit"})` + `@Import(TestcontainersConfiguration.class)`. A module test boots only its own module: `shared` holds the `Clock`, JSON, idempotency and notifier beans, `access` holds `AccessPolicy`, `audit` holds `AuditLog`. Add the modules your code calls. A use case that calls `requirePos` also needs a `StoreActivity` bean: include `"organization"` (and create the store), or declare a `@Primary StoreActivity` test bean (see `SseNotificationTest.AllStoresActive`); without one `requirePos` throws `IllegalStateException`.
- Act as a user with `@WithActor(permissions = {...}, storeId = "...")` (`com.xavier.backend.access.WithActor`, test sources): an `ACCOUNT`. Add `employeeId` and `terminalId` for a POS `EMPLOYEE` actor, whose principal id is then the employee id.
- SSE: subscribe with MockMvc (`request().asyncStarted()`), write in a `TransactionTemplate`, and poll the response bytes briefly (notices are sent off the committing thread; Awaitility is not on the classpath).
- Throw-away controllers for HTTP tests are static nested `@RestController`s pulled in with `@Import(Test.Probe.class)`. Spring's test scan skips nested classes of test classes.
- Architecture fixtures live in `com.xavier.archfixture.*`, outside the scanned base package.
