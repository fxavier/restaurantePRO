# Backend conventions

Owner: `software-architect`. Sources: [product_description.md](../product_description.md) (§6, §7, §9, §10, §12), [backend-decisions.md](../design/backend-decisions.md) (D1–D33), [r2-decisions.md](../design/r2-decisions.md) (D34–D63), [r3-decisions.md](../design/r3-decisions.md) (D64–D98), [r4-decisions.md](../design/r4-decisions.md) (D99–D136), the [ADRs](../adr/README.md), [PRD R1](../prd/r1-foundation-stage1.md), [PRD R2](../prd/r2-stage2.md), [PRD R3](../prd/r3-stage3.md), [PRD R4](../prd/r4-stage4.md). Each rule names the test that enforces it. A rule without a test is a wish.

## Modules

- One module per direct subpackage of `com.xavier.backend`. Every module has a `package-info.java` with `@ApplicationModule(allowedDependencies = {...})` following D13. Name only modules that already exist: Modulith rejects an unknown name. **Enforced by** `ModularityTests.modulesRespectTheirDeclaredBoundaries`. The `ModularityTests.anIllegalModuleDependencyIsDetected` test proves that verify fails.
- `shared` is `Type.OPEN`. It holds only technical types (D14) and depends on nothing.
- `access` holds the authorization primitives `com.xavier.backend.access.Permission`, `com.xavier.backend.access.Actor` and `com.xavier.backend.access.AccessPolicy` (D13 amendment, S0b). It depends only on `shared`, and its root types are public API for every module, so `organization` and `identity` can both use it without a cycle.
- `audit` depends on `shared` and `access` (D35): it reads the current actor for `recordAsCurrentActor` (D41).
- `config` holds the security filter chains (`config.security`), the correlation-id filter, scheduling configuration, the POS change stream (`NotificationController`) and the system endpoints (`SystemEventPublicationController`, D88). It depends on `shared`, `access` and `audit`. Nothing depends on it.
- Public API is the module's **root package** plus any `@NamedInterface` (`model/dto`, `model/event`, a `<Module>Api` facade). Entities, repositories, services and controllers stay in subpackages and are internal (D12).
- Facades (D36) are one per consumer concern (`DiningApi`, `CatalogApi`, `OrdersApi`, `OrdersProductionApi`, `CashApi`, `FiscalApi`). Their writes are `@Transactional(propagation = MANDATORY)`, so the coordinator (settlement) composes them in its own transaction, and they never authorize: the calling use case already did. For a resource addressed by id a facade offers a scalar store read (`OrdersApi.storeOf(orderId)`, `CashApi.storeOfDay(dayId)`, 404 when absent), so the caller authorizes on it (D42 (b)) before it takes any lock or loads anything (D51: the first lock belongs to an authorized use case). Coordinated closes (order, document, session, day) live in `settlement` (D37). Read-only label lookups for exports (R3): `OrganizationApi.findTerminal(terminalId)` (any status; `TerminalSummary.active()`), `DiningApi.tableInfo(tableId)` (`TableInfo(tableId, tableCode, areaId, areaCode, areaName)`) and `identity.EmployeeDirectory.summaries(ids)` (`Map<UUID, identity.EmployeeSummary(id, code, displayName)>`).
- R4 modules (D99, S37): `promotions` (→ shared, audit, access, organization(+dto), catalog(+dto), customers(+dto); public API `model.dto`, the frozen pricing records `PricingRequest`, `PricingLine`, `PricingResult`, `PricedLine`, `AppliedPromotion`, `DiscountLimits`) and `inventory` (→ shared, audit, access, organization(+dto), catalog(+dto, +event), orders(+event); public event `model.event.StockMovementsPosted(sourceType, sourceId, storeId, businessDate)`, with `@NamedInterface("event")` on the type). D99 also adds orders → promotions(+dto), customers(+dto); dining → customers; reporting → inventory(+event). Inventory listeners live in `com.xavier.backend.inventory.consumption`, reporting's R4 listeners in `com.xavier.backend.reporting.inventory` (the `EventPublicationStats.pendingFor` prefixes). Read facades added for R4: `OrdersApi.batchFacts(batchId)` (`BatchFacts`, the round's own lines; a transferred-in line is never in a round), `VoidFacts.consumedLineId` (the batch line a voided line descends from through transfers), `CatalogApi.items(ids)` (`ItemRef`, working copy) and `CustomersApi.address(customerId, addressId)` (`AddressSnapshot`).
- Module docs (D44): `ModularityTests.generatesModuleDocumentation` writes them to `backend/target/modulith-docs/` on every run and asserts each file exists. Only `rtk mvn test -Dtest=ModularityTests -Dmodulith.docs=true` writes the committed [modules/](modules/), and only the integration slice runs and commits that (the Documenter's output order is not deterministic). Slices never commit `docs/architecture/modules/`.

Module layout (D12): `model/`, `model/dto/`, `model/event/`, `repository/`, `service/`, `controller/`, `exception/`, `adapter/` (implementations of the module's outbound ports, e.g. `production/adapter` for the ESC/POS printer transport). Create a package only when it has content. The port interface stays where its callers see it (the module root when another module or a test supplies it, such as `settlement.PaymentProvider`); future payment-provider adapters (D53) go in `settlement/adapter/`, and existing packages are not moved.

## Shared contracts (S0)

- **Money**: `com.xavier.backend.shared.Money(BigDecimal amount, Currency currency)`. Construction never rounds and rejects excess decimals. `times(BigDecimal)` and `divide(BigDecimal)` are the only rounding points (HALF_UP to the minor unit; D59: `net = gross.divide(1 + rate/100)`, a zero divisor throws). `allocate(int)` and `allocate(List<BigDecimal>)` use largest remainder, so the parts always sum to the total. Mixing currencies throws `IllegalArgumentException`. Tested by `MoneyTest`.
- **Errors** (`shared.exception`): extend `NotFoundException` (404), `ConflictException` (409) or `BusinessRuleException` (422), one subclass per business meaning. A stale `@Version` (`OptimisticLockingFailureException`) gives 409. Bean Validation gives 400 with `errors: [{field, message}]`. `AccessDeniedException` gives 403 and `AuthenticationException` gives 401. Anything else gives 500 with no internal detail. Every error body is an RFC 9457 `ProblemDetail`. Tested by `GlobalExceptionHandlerTest` and `SecurityConfigTest`.
  - **Coded errors** (S7b, PRD R2 conventions): every R2 business-rule 422 and state 409 carries a stable `code` property that clients switch on; a code is never renamed once released. Pass it to the shared constructor: `new BusinessRuleException(String code, String message)`, `(code, message, Map<String, ?> properties)` and `(code, message, properties, Throwable cause)`; the same four on `ConflictException`; `NotFoundException(code, message[, properties])`. The handler renders `detail` = message, `code` (omitted when null: the one-argument R1 constructors stay uncoded) and each property (e.g. fiscal's `documentId`, catalog's `errors` list). Properties must not shadow `code`, `type`, `title`, `status`, `detail` or `instance` (`IllegalArgumentException`). Module subclasses expose `code()` and `properties()` from the sealed base `shared.exception.CodedException`; keep a typed accessor where callers need one (e.g. `CashRuleViolationException.rule()`). Tested by `GlobalExceptionHandlerTest`, `CodedExceptionTest` and `architecture.CodedErrorContractTest` (strict body: status, title, detail, instance, code, every extra property). Add a case there when you release a new code or property.
  - Do not subclass Spring's `ErrorResponseException` (ArchUnit `codedErrorsUseTheSharedExceptions`). The only exception is `identity.LoginThrottledException`: a 429 with `Retry-After` is neither a business rule nor a conflict.
- **Time**: inject `java.time.Clock` (UTC). The bean ticks in whole microseconds (`Clock.tick(Clock.systemUTC(), Duration.ofNanos(1000))`), because PostgreSQL `timestamptz` stores microseconds: an instant with nanoseconds differs from itself after a round trip (`ClockConfigurationTest`). Tests pin it with a `@TestConfiguration` that declares a `@Primary Clock`; keep a test clock microsecond-precise too.
- **Pagination**: accept a `Pageable` and return `PageResponse.from(page)`. Size is capped at 200 (`PageResponseTest`).
- **Idempotency** (D24, D47, D63): controllers of repeatable commands inject `access.IdempotentRequests` and return
  `idempotent.execute("<module>.<operation>", key, request, body, ResponseType.class, () -> ResponseEntity...)` (or `idempotent.steps(...)` for a command with an external-call step, D63), with `key` from `@RequestHeader("Idempotency-Key")`. It derives the scope `"<op>:<kind>:<principalId>"` (D38) from the current actor and the target `request.getMethod() + " " + request.getRequestURI()`, then calls `shared.idempotency.IdempotencyService.execute(String scope, String key, String target, Object body, Class<T> type, Supplier<ResponseEntity<T>> action)` (or `executeSteps`). It lives in `access` because the scope needs the `Actor` and `shared` depends on no module; do not write a module-local copy. Call it from the controller, outside any transaction: called inside one it throws `IllegalStateException` before claiming the key. The request identity is the SHA-256 of `target` plus the canonical JSON body. Approver code and PIN travel in the `X-Approver-Code`/`X-Approver-Pin` headers and are never part of the body (D40).
  - Same key and same target+body → the stored status, `Location` header and body are replayed; the body is deserialized into `T` (a `String` comes back as itself).
  - Same key with a different target or body → 422.
  - A duplicate while another request holds the key → 409. Only SQLSTATE 55P03 (lock_not_available) means that; a deadlock (40P01) or serialization failure (40001) propagates.
  - A missing, blank or over-255-character key → 400.
  - Only 2xx is stored (D47.3): business errors are **thrown**, which rolls back the action, so a retry with the same key evaluates the rule again. An action that returns a non-2xx `ResponseEntity` is a programming error (`IllegalStateException`, nothing stored).
  - Crash-safe: the action runs only while holding the record's row lock (`FOR UPDATE NOWAIT`), and its effects and the stored response commit together. After a crash or a failed action, the next request with that key takes the claim over and runs it once. The action's transaction is `READ COMMITTED`; take explicit short locks when you need more (D47.5).
  - Retention (D47.4): `IdempotencyRetention` deletes, daily at `restaurantpro.idempotency.retention-cron`, `COMPLETED` records whose `completed_at` and abandoned `IN_PROGRESS` claims (left by a crash or a refused action) whose `created_at` are older than `restaurantpro.idempotency.retention` (default `P90D`). A claim whose step lease is still live is kept.
  - Multi-step commands (D63): a command whose steps must run with no transaction, because one of them calls an external system (`FiscalApi.issue`, `provider.status`), uses `<T> ResponseEntity<T> executeSteps(String scope, String key, String target, Object body, Class<T> type, Supplier<ResponseEntity<T>> steps)` instead. It is called the same way, from the controller, and keeps the same hash, 422, replay, `Location` and 2xx-only rules.
    - The key is claimed with a lease (`lease_owner`, `lease_until` = now + `restaurantpro.idempotency.step-lease`, default `PT30S`). A live lease gives 409. An expired lease is taken over by compare-and-set, so only one of several concurrent retries wins.
    - The steps run with no transaction bound and no lock on the record. `ExternalCalls.requireNoTransaction()` is checked on entry and again after the steps return. Each step opens its own short transaction, so a request holds at most one connection at a time. **Every step must be idempotent by domain state**: the lease only suppresses duplicate work.
    - Only the lease owner can complete. If the lease was lost and the taker already stored its response, that response is replayed.
    - A thrown exception, or a non-2xx response (`IllegalStateException`), expires the lease and stores nothing. A retry with the same key then runs the steps again immediately. After a crash, the lease expires on its own.
    - **Each operation scope uses exactly one mode.** Use `execute` unless a step makes an external call. `executeSteps` refuses an unfinished claim made by `execute` (`IllegalStateException`). `execute` does not check for leases, so never mix the two modes within one scope (`IdempotencyStepsTest`).
  - **Per tenant** (R6, D186): `IdempotencyService` stores every record under the bound tenant: the key is `(tenant_id, scope, key)`, `tenant_id` taken from the transaction's binding (the column default) and filtered by row-level security, a TENANT table; the scope string stays `"<op>:<kind>:<id>"`: the same key in two tenants is two records and a replay never crosses tenants. Its reads run in a short read-only transaction of their own (the table is protected, D178), and the retention job runs once per tenant (`IdempotencyTenantScopeTest`).
  - Never write your own (`IdempotencyServiceTest`).
- **External calls** (D48): the action of `execute` runs in a DB transaction, so it never calls an external system. Payment provider and remote fiscal calls use "persist, then call, then record": the domain row (e.g. a `PaymentAttempt` in `CREATED`) is the claim, a compare-and-set moves it to `PENDING` so exactly one submitter calls, the call runs with no transaction or lock, and a second transaction records the outcome (`UNKNOWN` on timeout). Every adapter's first line is `ExternalCalls.requireNoTransaction()`, which throws `IllegalStateException` when a transaction is active or a connection/`EntityManager` is bound to the thread (`ExternalCallsTest`).
- **Persistence helpers** (D43): `shared.persistence.UniqueConstraints.saveAndFlush(repository, entity, () -> new XTakenException(...), "x_uk", ...)` turns a violated named unique constraint (also one lost in a race) into its 409 exception; `UniqueConstraints.isViolated(e, names...)` for the rare multi-branch case. `shared.persistence.OptimisticLocking.requireVersion(Type.class, id, stored, sentByClient)` gives 409 for a stale client version. Never copy them into a module (`UniqueConstraintsTest`; each module's race tests).
- **Change notices** (D60): a use case that changes what a POS screen shows calls `changeNotifier.notifyAfterCommit(storeId, ChangeTopic.X, id)` inside its transaction (`IllegalStateException` outside one). Clients on `GET /api/v1/pos/notifications` (`text/event-stream`, store from the session, `DINING_VIEW` or `PRODUCTION_VIEW`) receive `{topic, id}` after the commit, nothing after a rollback, and never data: they re-read through the authorized GET. Topics: `TABLES`, `ORDER`, `CATALOG`, `PRINT_JOBS`, `PAYMENT_ATTEMPT`. No replay, 25 s heartbeat, 30 min emitter timeout (`SseNotificationTest`). **Delivery** (R6, D185 as amended): the notice is `pg_notify('change_notice', '<tenantId>:<storeId>:<topic>:<id>')` on the writing transaction's connection, so PostgreSQL delivers it on commit only, to every backend instance; each instance holds one `LISTEN change_notice` connection of its own (not from the pool) and forwards to its streams keyed `(tenantId, storeId)`, the tenant being the subscriber's bound one, so another tenant's stream never receives it, even for the same store id (`NotificationTenantIsolationTest`). `ChangeNotifier` is a `SmartLifecycle` that completes every stream before the web server's graceful shutdown, so an open stream does not hold the shutdown (D89 (3), `ChangeNotifierShutdownTest`). Notices and heartbeats are written by the notifier's single sender thread, never by the committing or scheduler thread; a timed-out emitter is completed, so the client simply reconnects (`ChangeNotifierStreamTest`).
- **Scheduling** (D46, D185 as amended): `@EnableScheduling` is on (`config.SchedulingConfig`). Put a job in a `@Service` (repositories are used only from services). A job names its scope with `@SystemScoped`; the advisor runs a reach-`ALL` job **once per ACTIVE tenant** (`tenancy.active_tenant_ids()`, from a rotating start), each in that tenant's binding and under a lease per `(job, tenant)` (`shared.tenancy.JobLeases`, `shared.job_lease`, compare-and-set, `restaurantpro.jobs.lease-ttl` PT2M, released when the run ends), so two backend instances never run the same job for the same tenant at once; a suspended or provisioning tenant is skipped, and one tenant's failure is logged with its tenant, counted (`system_job_tenant_failures{job}`) and does not stop the others. Called from a thread already bound to a tenant (a request, a test), it runs once there. A reach-`NONE` job runs once with no tenant (PLATFORM tables only). `SystemScope.BOOTSTRAP` runs in the bootstrap tenant only. No job iterates tenants itself, and no job holds a cross-tenant scope (`ActorlessTenantScopeTest`, `JobLeaseTest`). Jobs must still stay correct under overlap (`SKIP LOCKED`, compare-and-set updates), and handle a bounded batch per tenant per tick (`restaurantpro.jobs.batch-per-tenant`).
- **Audit** (D20, D41): inside the use case's `@Transactional` method call `auditLog.recordAsCurrentActor(action, entityType, entityId, storeId, approverId, reason, details)`: actor id, actor kind and terminal come from the session. A write nobody asked for in a session (bootstrap, scheduled job, listener, device enrolment) uses `auditLog.recordAsSystem(action, entityType, entityId, storeId, terminalId, reason, details)` (`actor_kind = SYSTEM`, no actor). `recordAs(actor, ...)` is only for login and logout. All require an existing transaction (`MANDATORY`). There is no hand-filled `AuditEntry` path. `audit_event.terminal_id` is where the actor acted, not the entity (the entity is `entity_type`/`entity_id`). Details carry no PIN, password, token or card data, and keys that look like secrets are rejected at any depth: the guard walks nested maps and the maps inside lists (D82). Every key is a field name, matched case-insensitively (`pin`, `PIN`, `approverPin`, `CARD_NUMBER` are all rejected), so data codes are values, never keys: `"counts": [{"methodCode": "CASH", "amount": "10.00"}]`. It checks keys, not values. The database refuses UPDATE, DELETE and TRUNCATE on `audit.audit_event`, a `SYSTEM` row that names an actor, and an `ACCOUNT`/`EMPLOYEE` row without one (`AuditLogTest`).
- **Authorization** (D27): the first line of every BackOffice use case is `accessPolicy.require(Permission.X, storeId)` (or `require(Permission.X)` for installation-wide operations). Controllers never authorize. Authorities are `PERM_X` (all stores) and `PERM_X@<storeId>`. `Actor.authorities()` is the only source for these decisions; login builds the `Authentication`'s granted authorities from the same set (actuator URL rules read those). Denials are logged at WARN (`AccessPolicyTest`, `SecurityConfigTest`). `Permission` is append-only; a new constant needs a migration that grants it to the administrator role (`RoleSeedTest`).
- **Actor** (D38): `Actor(ActorKind kind, UUID userId, UUID employeeId, UUID terminalId, UUID storeId, Set<String> authorities)`. `userId` is the principal id: the account for `ACCOUNT`, the employee for `EMPLOYEE` (then equal to `employeeId`; an `ACCOUNT` has no `employeeId`). Build it with `Actor.account(...)` / `Actor.employee(...)`. Business facts store typed columns, never the bare `userId`: POS facts `*_employee_id`, BackOffice facts `*_account_id`. Changing `Actor`'s shape invalidates stored sessions: a stored attribute this release cannot read is treated as absent (`config.SessionConfig`), so the user gets 401 and logs in again (`OutdatedSessionTest`). Note that a record's `serialVersionUID` is not checked by Java serialization; the canonical constructor's checks are what reject an old shape.
- **POS context** (D39, D45): every POS use case starts with `PosContext pos = accessPolicy.requirePos(Permission.X)` (or `requirePosAny(...)`) and takes `pos.employeeId()`, `pos.terminalId()`, `pos.storeId()` from it. POS write endpoints never take a store or terminal from the request. `requirePos` gives 403 unless the actor is an `EMPLOYEE` with a terminal, holds the permission in the session's store, and that store is active (`access.StoreActivity`, implemented by `organization`, cached per request). A BackOffice session calling a POS write gets 403 (`AccessPolicyTest`). Only `access.AccessPolicy` reads the security context: code that runs both in and out of a session (an audit that records the current actor or the system) asks `accessPolicy.currentIfPresent()` (`Optional<Actor>`), never `SecurityContextHolder`, and never for an authorization decision.
  - A POS read that accepts an optional `?storeId=` calls `accessPolicy.requirePos(Permission.X, requestedStoreId)`: `null` means the session's store, another store gives 403 (logged). For a resource addressed by id, after `requirePos(Permission.X)` and the 404 read of its `storeId`, call `accessPolicy.requireSessionStore(pos, resourceStoreId, ENTITY, id)`: 403 when it is another store, and the denial log names the resource.
- **Approvals** (D40, D28): an approved command runs in two phases. The controller first calls the service's non-transactional `authorize...(id, approverCode, approverPin)`, which calls `ApproverVerifier.verify` and returns the module's `service.Approval` record; then `idempotency.execute(...)` runs the transactional apply with it. Never verify an approver inside the use-case transaction (a second connection, and the order lock held for the BCrypt time). The approver must not be the operator (422 `SELF_APPROVAL`).
- **Any of several permissions** in a store (BackOffice): `accessPolicy.requireAny(storeId, Permission.A, Permission.B)` passes when any one is held installation-wide or `@storeId`, and logs one denial naming all of them. Never test `actor.authorities()` by hand.
- **Company-wide data and store-filtered queries** (R3, R4): company-wide data (customers P38, suppliers, stock items, recipes, the loyalty program) is read with `accessPolicy.requireInAnyStore(Permission.X)`: it passes when `X` is held installation-wide or in at least one store. **Writes to company-wide data need `X` installation-wide: `accessPolicy.require(Permission.X)`** (D125 amendment): a permission held in one store must not change what every other store uses. As built: suppliers and supplier items (`PURCHASE_MANAGE`), stock items (`INVENTORY_MANAGE`), promotions (`PROMOTION_MANAGE`), the loyalty program (`LOYALTY_PROGRAM_MANAGE`), loyalty adjustments (`LOYALTY_ADJUST`), credit limits (`CREDIT_LIMIT_MANAGE`), the balance rebuild (`INVENTORY_REBUILD`). Known deviation, reported in S54 for `solution-architect`: recipes and consumption policies (`RECIPE_MANAGE`, PRD S47) are company-wide but are written with `requireInAnyStore`. A query that filters its rows by store (audit D82, reports D86) asks `AccessScope scope = accessPolicy.scopeOf(Permission.X)`: `scope.global()` (installation-wide holder, who also sees store-less rows), `scope.stores()`, `scope.includes(storeId)`. Both give 403, logged, when `X` is held nowhere (`AccessPolicyTest`).
- **Store-scope check order** (D42): (a) when the store is an input (the POS session, or a `storeId` in the body or query), call `require`/`requirePos` before any read; (b) for a resource addressed by id, read only its `storeId` (404 if the row is absent), then `require` (403). Never load fully, then authorize. Every module adds a test for both orders (R2 slices; R1 modules follow when touched).
  - **Across tenants** (R6, D179, security rule 5): a resource of **another tenant** addressed by id is **absent (404)**, with no hint that it exists; a resource of **another store of the same tenant** is **forbidden (403)**. Both come for free from the rules above: row-level security hides another tenant's row from every read, and the probe `shared.persistence.StoreProbe` (`shared.store_of`, SECURITY DEFINER) answers the store only for a row of the bound tenant, `NULL` (404) otherwise, and `RS003` with no tenant bound (`StoreProbeTenantTest`, `OrganizationTenantIsolationTest`).
- **Tenant** (R6, D177, D178): every request, job, listener and task runs in exactly one tenant, `shared.tenancy.TenantContext(tenantId, kind, principalId, origin)`, read through `shared.tenancy.TenantScopes` (`current()`, `requireTenant()`). Resolution order: an explicit binding (`TenantScopes.run/call(tenantId, SystemScope, …)`, a listener's event, a propagated task), else the authenticated principal's resolved membership, else the request's pre-resolution tenant (the bootstrap tenant, `BootstrapTenantRequests`, until S72 resolves it from the JWT), else none. A tenant never comes from a request: no controller parameter, path or query value, header or request DTO component named `tenantId` (ArchUnit `noTenantIdFromRequests`); `X-Tenant-Id` only selects among the caller's memberships (S72). Only `config.security` and `TenantScopes` create a `TenantContext` (`onlyResolutionCreatesTenantContext`). A use case never takes or passes a tenant: inserts take it from the column default and every read is filtered by row-level security. `TenantScopes.run/call` refuse to start inside a transaction, as `StoreScopes` does (`TenantScopesTest`).

## Operations: alerts and metrics (R5)

- **`shared.ops`** (D149, ADR 0037): `AlertSource { List<OperationalAlert> alerts(); }` is implemented next to the data, in the module that owns it (production's print queue, settlement's in-doubt attempts, cash closings, `shared.events` publications, `config.alerts` for the backup status file and disk). A source must be fast: it reads an in-memory gauge snapshot or runs one indexed query on its own module's tables (prove the index with an EXPLAIN test of the query's SQL, pinned to the repository query so the two cannot drift, e.g. `PrintJobUnresolvedPlanTest`), because `config.alerts.AlertsService` calls every source when its 30 s cache expires. A failing source becomes one `ALERT_SOURCE_FAILED` alert, never a 500. `OperationalAlert.storeId` is `null` for installation-wide conditions, which only an installation-wide `SYSTEM_MONITOR` holder sees. `shared.ops` depends on no module (`sharedOpsDependsOnNoModule`).
- **Exports run inside `ExportMonitor.monitor(kind, supplier)`** (`report_csv`, `audit_csv`, `inventory_csv`): it counts `exports_total{kind, outcome}` and remembers the last failure for `EXPORT_FAILED`. A new export (a fiscal adapter's, later) uses it with a new `kind`.
- **Metric and alert labels** (D149, §12): tag keys only `store`, `status`, `state`, `module`, `kind`, `outcome`, `name`, `job` (plus Micrometer's own JVM and HTTP keys). **Never `tenant_id`** (R6, P74): per-tenant health is a log line with the tenant and an in-app alert computed inside the tenant, not a label. Never an order, payment, job, document or account id, as a tag value or in an alert summary (`MetricLabelsTest`, and every Prometheus rule summary in `deploy/monitoring/alert-rules.yml`). A per-store `MultiGauge` has no series until its first refresh with a row; Prometheus reads an absent series as "no alert", and a test that scrapes for a metric must refresh first (`R5AcceptanceTest`). `AlertRulesReferenceExistingMetricsTest` keeps the rules and the backend's metric names together.
- **Console audit function** (D143, V1105): a host script that changes data outside the application (`deploy/mfa-break-glass.sh`) writes its audit row through `audit.record_console_event(action, entity_type, entity_id, reason)` (actor NULL = system, `details = {"via": "console"}`), in **one** `psql` transaction with the owning module's own function (`identity.mfa_break_glass_reset`), so each schema is written only by its module's function (D6) and both commit or neither (`BreakGlassFunctionTest`).

## Persistence

- Flyway, one history, `db/migration/<module>/V<block>__<module>_<what>.sql` with blocks shared/audit 1xxx, organization 2xxx, identity 3xxx, dining 4xxx, catalog 5xxx (D5), orders 6xxx, production 7xxx, cash 8xxx, settlement 9xxx, fiscal 10xxx (D61), customers 11xxx, promotions 12xxx, inventory 13xxx, reporting 14xxx, tenancy 15xxx (R6). Existing modules use the next free number in their own block. Never edit an applied migration.
- One schema per module (`CREATE SCHEMA IF NOT EXISTS <module>`), with no cross-module foreign keys (D6). Constraints back every invariant they can express.
- `spring.jpa.hibernate.ddl-auto=validate`: entities must match the migrations, and every context start checks it.
- UUIDv7 ids: `@UuidGenerator(style = VERSION_7)`.
- **Tenant tables** (R6, D179, D180 as amended, security rules 2 and 3): every new table is classified TENANT* or PLATFORM. A tenant table gets, in its module's migration and in this order: `tenant_id uuid NOT NULL` (an existing table: `ADD COLUMN … DEFAULT '<bootstrap uuid>'`, catalog-only, then) `DEFAULT shared.rls_tenant_id()`; `UNIQUE (tenant_id, id)`; every business unique key as `(tenant_id, …)` (keep the old constraint name: `UniqueConstraints` maps by name); every in-module foreign key composite `(tenant_id, x_id) REFERENCES parent (tenant_id, id)` (`NOT VALID`, then `VALIDATE`); then the helper of its class: `shared.rls_protect_tenant_table` (TENANT: restrictive `tenant_scope` + permissive `tenant_rows`), or the store helpers of V1008/V1009, which call `shared.rls_protect_tenant` first when the table has `tenant_id` (restrictive `tenant_scope` ANDed with the store policy, `tenant_fixed` RS002 trigger, `shared.rls_tenant_table`). A table already store-protected calls `shared.rls_protect_tenant` directly. No `UPDATE` in these migrations. A PLATFORM table is registered with `shared.rls_register_platform(t, reason)`. The entity maps `tenant_id` read-only (`insertable = false, updatable = false`) or not at all; no use case writes it. A converted module joins `RowLevelSecurityCoverageTest.TENANT_PROTECTED_MODULES` (`assertModuleTenantProtected`, `CompositeForeignKeyCoverageTest`).
- **Statements on protected tables run inside a transaction** (R6, D178): the tenant and the store scope are bound at transaction begin (`config.persistence.TenantBindingTransactionManager`, `set_config(…, true)`), so an autocommit statement carries nothing and a protected table raises `RS003` (no tenant) or `RS001` (no store scope). A `JdbcClient` statement outside a `@Transactional` method belongs in a short `TransactionTemplate` (`IdempotencyService`, `IdempotencyRetention`, `JobLeases`, `StoreProbe`). As a default, declared Spring Data query methods without their own `@Transactional` get a `REQUIRED` transaction (`RepositoryQueryTransactions`), like the base methods, and so do the public methods of a hand-written `@Repository` class (`RepositoryClassTransactions`): called outside a transaction each opens a short bound one, inside one it joins. Never `set_config(…, false)` and no session-level setting anywhere (PgBouncer in transaction mode, D188); a refusal is mapped to 500 `TENANT_SCOPE_MISSING` (`RS003`) or `TENANT_SCOPE_VIOLATION` (`42501` on `tenant_scope`) and counted (`TenantBindingTransactionManagerTest`).
- **Caches** (R6, D186 as amended, security rule 7): no Spring cache (`@Cacheable`, `CacheManager`) and no Caffeine outside `shared.tenancy.TenantScopedCache`, which does not exist yet: the allow-list is empty (ArchUnit `cachesAreTenantScoped`). An in-memory memo keeps the tenant in its key (`(tenantId, …)`); a per-bean gauge or alert state is computed per tenant through the job iteration.
- **Locks** (D17, D51). Human edits use `@Version` (409). Short pessimistic locks only where the decisions name them, always in this order within a transaction, and never held across a call that leaves the JVM:
  - settlement (D76, amends D51): `order_settlement` (`SettlementLocks`, the first lock of every pay, issue, close, partition and credit command) → `customers.credit_account` (`CustomersApi.lockAccount`/`reserve`) → `cash_session` / `cash_day` → fiscal (`fiscal_document` before `fiscal_series`). A debt payment starts at `credit_account` (it has no order). Never take `credit_account` before `order_settlement`: a credit sale and a payment of the same order would lock in opposite orders.
  - orders: claim an order by moving its version first (`OrderLookup.claim`); several orders are claimed in ascending id order (transfers, merge). A table opening or move writes the order row (and its open-table unique entry) first, then calls `DiningApi` (occupation and table `FOR UPDATE`).
  - dining: table, then area (`DiningRows`).
  - **R4 order** (D132, amends D76): `order_settlement` → `orders.order_header` (version claim) → `orders.order_line` of a reward holder (`FOR NO KEY UPDATE`, D112a, voids only, right after the void's own version claim) → `customers.credit_account` → `promotions.loyalty_account` → `cash_session` / `cash_day` → `fiscal_document` → `fiscal_series`. Loyalty earning takes no `FOR UPDATE` (insert-only; the EARN entry's foreign key takes `FOR KEY SHARE` on `loyalty_account` in that row's place). Proofs: `LoyaltyRedeemRaceTest`, `DiscountVersusPaymentRaceTest`, `DiscountConcurrencyTest`, the D133 races.
  - inventory (D113, D132): **never in the same transaction as any lock above** (it runs in its own listener or command transaction). Within inventory: first the order-line advisory locks (`ConsumptionBook.lockLines`, `pg_advisory_xact_lock(hashtextextended(lineId, 47))`, in id order: a round, a void and a reprocess of the same line serialize), **then** `stock_balance` `FOR UPDATE` in `BalanceKey.LOCK_ORDER` (ascending `(warehouse_id, stock_item_id)`). A caller that posts more than once in a transaction (a same-store transfer, a count, a receipt in steps) calls `StockLedger.lock(allKeys)` before its first `post`, because each `post` sorts only its own keys. Proofs: `StockPostingDeadlockTest`, `TransferDeadlockTest`, `SaleAndTransferLockTest`, `CountApprovalSaleDeadlockTest`, `AverageCostConcurrencyTest`.
  - production: printer rows in id order (`PrinterRepository.lockAll`), mode change only (D51 amended). The print worker's claim locks jobs with `FOR UPDATE OF j SKIP LOCKED`: each printer's head job if due, none for a printer with a PROCESSING job (D50 §7.2 amended).
  - **Decide on the locked row.** A locking JPQL query on an entity the transaction already manages takes the lock but returns the stale instance. Lock with `find` + `refresh(entity, lockMode)` (`cash.service.RowLocks`, `dining.service.DiningRows`), or a compare-and-set `UPDATE … WHERE status = ?` with a row-count check (`PaymentAttemptRepository.markSubmitted`).

- **Payment target key** (D69): an attempt, payment and allocation carry `target_type` (ORDER, PARTITION, CREDIT_ACCOUNT) and the generated `target_key = coalesce(partition_id, order_id, credit_account_id)`. Balances, the one-open-attempt rule and allocation uniqueness are per target key; never key them on `order_id` alone (a partition's rows keep their order id).
- **Residual-only tax placement** (D96): the tax cent a settled void leaves is placed only when the residual ORDER document is drafted (close s1, `/documents`, an ORDER-target credit sale s1), under `order_settlement`, in the drafting transaction, before `FiscalApi.createDraft`, by `TaxRoundingAdjustments`. Never at void time, never on a partition draft, never by changing gross or an order line. A retried draft re-applies the stored `tax_rounding_adjustment` rows instead of placing again; what cannot be absorbed becomes a PENDING_CORRECTION row and an issued document is never touched.
- **Stock valuation** (D113 as amended, [ADR 0031](../adr/0031-stock-ledger-and-moving-average.md)): `inventory.service.StockLedger.post` is the only path that writes movements and balances; S47–S49 code never inserts movements. An OUT at stock ≥ 0 takes `−round4(V × q ÷ Q)`, emptying takes `−V`; crossing or below zero `−round4(q × avg)` (`MovingAverage`). **An explicit value is given only to a `CONSUMPTION_REVERSAL` or a `TRANSFER_IN`** (at its own cost, ≥ 0), or as a `REVALUATION`'s value: `PostMovement`'s constructor throws for any other (`PostMovementTest`). A `TRANSFER_IN` carries exactly its `TRANSFER_OUT`'s posted value; a reversal or waste share is at most what is left of the sale's value. **Never compute a value from `q × unitCost` when a posted value exists**: read the posted value (`TransferValueTest`, `VoidReversalTest`).
- **Cost variance sign** (D125 amendment, inherited by reporting): a positive `cost_variance.value` always means **more cost of goods**. Corrections: the consumed share of `(new − previous) × quantity`. Linked supplier returns: `(average − receipt cost) × quantity`. The purchases report values a return at the supplier's credit, `|OUT value| − variance`; margin = net sales − (SALE_CONSUMPTION − CONSUMPTION_REVERSAL value) − cost variance (`CostCorrectionTest`, `SupplierReturnCostTest`, `MarginReportTest`).
- **Rewards** (D112a): "does this line carry a reward" is asked only of `orders.service.RewardLineage` (the line's ancestry through transfers and splits made after the reward), never of a line's own adjustment history: a second reward, a REVERSAL, earning, the bill label and the void's points all go through it (`RewardRedemptionTest`). The price origin and label of a copy follow the same lineage walk, only at that adjustment's price (D107 amendment, `OfferLineageTest`).
- **Activation** (D122 amendments): `activeFrom` is optional (now); more than 60 s in the past → 422 `ACTIVATION_IN_PAST`. Starting an OPENING count makes the store live (`ActivationHttpTest`, `OpeningCountTest`).
- **The single issue path** (D97): every settlement issue goes through `settlement.service.SettlementIssuer.issue(pos, orderId, documentId)`: a short transaction (`order_settlement FOR UPDATE` → snapshot → `FiscalApi.recordPayments`, MANDATORY), then `FiscalApi.issue` with no transaction. No other class outside fiscal calls `FiscalApi.issue` or `FiscalApi.recordPayments` (ArchUnit `onlySettlementIssuerCallsFiscalIssue`, `SettlementIssuerRuleTest`).

## Events

- Cross-module events go through the Spring Modulith JPA publication registry (`event_publication`, D19). Listeners use `@ApplicationModuleListener` and must be idempotent.
- **Every event carries its tenant** (R6, D185, security rule 6): an event record's first component is `UUID tenantId`, set at the publish site from `TenantScopes.requireTenant()` (never from a request). The scope advisor binds a listener to its event's `tenantId` (and its `storeId` or `@SystemScoped` scope) before the listener's `REQUIRES_NEW` transaction; an event without a tenant fails before it, and stays incomplete for the D88 recovery. `event_publication*` is PLATFORM: the startup republication and the recovery read it across tenants, and the serialized event brings its tenant back (ArchUnit `eventsCarryTenantId`; `ActorlessTenantScopeTest`). A record that is only a part of an event (`orders.model.event.Line`) needs none.
- `spring.modulith.events.republish-outstanding-events-on-restart=true`: when the application starts, it delivers again every publication whose listener had not completed. This is safe because each installation runs one instance. `EventRepublicationTest` proves it with a real second application context started on the same database.
- **Runtime recovery** (D88): `shared.events.EventPublicationRecovery` resubmits, every `restaurantpro.events.resubmit-interval` (PT1M), each incomplete publication untouched for `resubmit-older-than` (PT5M, since its publication or last resubmission) with fewer than `max-attempts` (10) attempts, through Modulith's `IncompleteEventPublications`. The attempt count is Modulith's `completion_attempts`, which counts the first delivery as attempt 1. Past the limit a publication is `FAILED` for a person: `GET /api/v1/backoffice/system/event-publications?state=INCOMPLETE|FAILED` and `POST …/resubmit {publicationIds | olderThan}` (`SYSTEM_MONITOR` installation-wide, the POST audited `EVENT_PUBLICATIONS_RESUBMITTED`, 202 `{selected}`; a manual resubmission ignores the limit). `spring.modulith.events.staleness.resubmitted=PT10M` frees a publication a crash left `RESUBMITTED` (Modulith never resubmits one in that state). Completed publications older than `completed-retention` (P30D) are deleted daily. `EventPublicationStats.pendingFor(listenerIdPrefix)` counts a listener's pending publications (partial index V1006), and the gauge `event_publications{state="incomplete"|"failed", module}` (the listener's module) counts them all (`EventPublicationRecoveryTest`, `EventPublicationStatsTest`, `SystemEventPublicationHttpTest`).
- **Subtotal request id** (D89 (2)): `SubtotalRequested.requestId` is a UUIDv7 per subtotal command (an Idempotency-Key replay publishes nothing). A publication stored by R2 deserializes with `requestId = null` (`SubtotalRequestIdTest`).

- **Reporting is read-only** (D65, D84): reporting listeners pull facts through read-only facade methods (`@Transactional(readOnly = true)`, ArchUnit `reportingCallsOnlyReadOnlyFacadeMethods`) and upsert keyed by the source id (`ON CONFLICT DO NOTHING`); nothing depends on reporting, and a projection never produces a receipt, a credit or stock. Rebuild uses the same pull code path.

## Web and security

- **Bearer JWT on the API** (R6, D176, `config.security`): the backend is an OAuth2 resource server for Keycloak's two realms. Every BackOffice and `/auth/**` call carries `Authorization: Bearer <access token>`; validation is complete and fail closed (`BearerAuthentication`): `RS256`/`ES256` only, `iss` exactly the realm's issuer (`restaurantpro.security.issuers.tenant`/`.ops`), `aud` contains `restaurantpro-api`, `exp` required and `nbf`/`iat` not in the future (skew `restaurantpro.security.clock-skew`, on the injected `Clock`), claim `typ = Bearer` (an ID or refresh token is never an access token), `azp` allowed for the route family (`RouteFamily`: `backoffice-bff` → `/backoffice/**`, `/auth/**`; `bridge-*` → `/bridge/**`). The key sets are fetched lazily (the backend starts with Keycloak down); a call that cannot be verified is 503 `IDP_UNAVAILABLE`, and so is every call while the issuers are unset. Claims never grant authority. Tests: `JwtValidationTest`, `IdpUnavailableTest`, `KeycloakLoginIT`.
- **Tenant from the membership** (D177, `TenantResolutionFilter`): `X-Tenant-Id` only selects among the token's `(iss, sub)` memberships, read on every request (`TenancyApi.resolve`, no cache); the ops realm resolves `SUPPORT` memberships only. Refusals: 400 `TENANT_SELECTION_INVALID`/`TENANT_SELECTION_REQUIRED`, 403 `TENANT_FORBIDDEN` (one body for a foreign and a random tenant), `TENANT_SUSPENDED`, `TENANT_CLOSED`; `/platform/**` needs an ops token with `platform-operator` (403 `PLATFORM_FORBIDDEN`). The actor is then built from the tenant's rows inside the tenant's binding (`access.ActorDirectory`, identity's `PrincipalActors`) and the request runs as `access.ActorAuthentication`; every log line after it carries MDC `tenant_id` (`TenantMdcLogContractTest`). `GET /api/v1/auth/tenants` lists the caller's own memberships.
- **No session, no cookie, no CSRF on the API**: the credential is a header a browser never sends on its own. The BFF (P69, `bff/`) keeps its own cookie session with CSRF. Tests act with `@WithActor`, `TestAuthentications.of(actor, tenant)` or `TestJwtFactory` (`config.security` test sources, trusted by `TestJwtAutoConfiguration`); the Keycloak Testcontainer is for the identity and end-to-end suites only.
- **POS, interim until S73**: the POS routes (`RouteFamily.POS`: `/api/v1/pos/**` and the PIN login routes under `/auth`) authenticate with `X-Pos-Session` (the opaque token of the PIN login, kept as SHA-256 in `identity.terminal_session`, idle 30 min, 10 h at most) and run in the bootstrap tenant (`InterimPosBootstrapTenant`, the only constant request tenant, `NoConstantRequestTenantTest`); 401 `POS_SESSION_INVALID` without a live session. S73 adds the terminal's bearer token and `TERMINAL` membership and deletes the interim class.
- Actuator runs on the management port (8081 by default). `health` is open. Every other endpoint needs `PERM_SYSTEM_MONITOR`.
- `ASYNC` and `ERROR` dispatches are permitted (the original request was authorized; the SSE stream completes on an async dispatch).
- The Hikari pool holds 20 connections (D40: 10 terminals; approver verification commits on its own connection before the use case's transaction).
- Every response carries `X-Correlation-Id`, and every JSON (ECS) log line carries `correlationId` (`CorrelationIdTest`).
- **Audit details never carry secrets** (§10, D82): `AuditEntry` rejects a secret-looking key (`pin`, `password`, `secret`, `token`, `card`, `pan`, `cvv`, …) **at any depth**, walking nested maps and the maps inside lists (substring and case-insensitive: `approverPin`, `CARD_NUMBER`), so a secret must never be a value under an innocent key either.
- **Backup keys** (D98): only the public age recipients (operational and recovery, two custodians) are on the server; an identity (`AGE-SECRET-KEY-1`) is never stored under `deploy/` or the backup directory, and the scripts refuse to run when one is found. Restores take `--identity FILE` on a restore host. Production (`RESTAURANTPRO_ENVIRONMENT` unset or `production`) never writes a plaintext backup.

- **Step-up for sensitive permissions** (D142 as amended by D184, RFC 9470): `Permission.sensitive()` marks the fixed set of D142 (one `EnumSet`; adding a constant to it is a decision, not a code change). `AccessPolicy` asks, after the permission check itself, for an `ACCOUNT` actor whose granting permission is sensitive, that the request's own token proved a second factor (`acr ≥ 2`) at most `restaurantpro.security.step-up-max-age` (PT5M) ago (`auth_time`), read from `ActorAuthentication.assurance()`; any other authentication proves nothing. Otherwise 401 `MFA_STEP_UP_REQUIRED` with `WWW-Authenticate: Bearer error="insufficient_user_authentication", error_description="A different authentication level is required", acr_values="2", max_age=300`. A POS (PIN) session using a sensitive permission outside `requirePos*` is 403 `MFA_ACCOUNT_REQUIRED`. Support needs `acr ≥ 2` on every request (D183). It applies to `require`, `requireAny` (all granting permissions sensitive), `requireInAnyStore` and `scopeOf`; `requirePos*` and approver PINs never ask. A 401 is never stored by idempotency, so the client retries with the same key after stepping up through the BFF and the command runs once (`StepUpTest`).
- **Security chains** (`config.security.SecurityConfig`, `ApiSecurity`): actuator, POS (interim) and API chains, plus `config.MetricsScrapeSecurity`'s Prometheus chain, which reuses `ApiSecurity`. Never a `Customizer<HttpSecurity>` bean: Spring Security 7 applies those to **every** `HttpSecurity`, including the actuator and Prometheus scrape chains.

## Tests

- Real PostgreSQL only: `@Import(TestcontainersConfiguration.class)`. One `postgres:18.6-alpine` container serves the whole JVM. Tests share the database, so use fresh UUIDs and keys per test and never assume empty tables.
- **Store scope in tests** (ADR 0039, D171). Every test runs production code as `restaurantpro_app`, bound by row-level security; privileged fixtures (`TRUNCATE`, `DISABLE TRIGGER`, `ANALYZE`, DDL, reads across stores outside a test body) go through `OwnerDatabase`.
  - The **fixture fallback** (all stores, origin `test-fixture`) lives in the test-only auto-configuration `StoreScopeTestAutoConfiguration`, not in `TestcontainersConfiguration`; it also re-registers the scope hook and advisor in every `@ApplicationModuleTest` context. It applies only on the JUnit thread during a test method, with neither an actor nor an explicit scope. `@BeforeAll`/`@AfterAll` SQL on a protected table needs `OwnerDatabase` or an explicit `StoreScopes` call.
  - MockMvc requests run with production semantics (`FixtureFreeRequests` unmarks the thread while they dispatch): the actor's stores, or `STORE_SCOPE_MISSING` with no actor. `asyncDispatch` and `standaloneSetup` are not covered by that filter.
  - **Awaitility** poll threads inherit the awaiting thread's fixture mark and security context, so a condition needs no `pollInSameThread()`. Listener, scheduler and executor threads are always strict.
  - An application a test starts or closes itself (`SpringApplicationBuilder`, the restart tests) runs its startup and shutdown **unset**, as production does.
  - `@StrictStoreScope` turns the fallback off for a class (the isolation suites); such a class seeds with `StoreScopeTestSupport.inStrictFixture(…)` (the test-only fixture scope), never with a production `SystemScope`. `StoreScopeTestSupport.asFixture(…)` clears the actor for a fixture that seeds another store.
  - The A71 seam is `com.xavier.backend.AppRoleSession`: one `restaurantpro_app` connection whose scope the test writes (`stores(…)`, `allStores()`, `unset()`). `RS001` needs a reached row: seed a row before asserting it.
  - A new table is classified in its module's migration (`RowLevelSecurityCoverageTest`, all schemas); a new listener or job gets a case in its module's `<Module>ActorlessScopeTest`.
- **Tenant in tests** (R6, D189 as amended). Existing tests run in the **bootstrap tenant** (`TenantTestSupport.BOOTSTRAP`, the migrations' literal) without change: the tenant fallback (`TenantTestSupport.FALLBACK`, the `@Primary` `TenantFallback` of `StoreScopeTestAutoConfiguration`) answers it on the marked JUnit thread, and on a thread a test runs as an `Actor` (a request it emulates off MockMvc); `@WithActor` binds it as the actor's resolved tenant (`tenantId` overrides it). Listener, scheduler and executor threads, and an application's own startup, are unbound, as in production.
  - **Autocommit SQL in a test body**: production binds only at transaction begin, so the test-only `FixtureCheckouts` writes, at every checkout and on the test connection only, the thread's resolved tenant and store scope when the thread runs a test body, and nothing on every other thread (D171's mechanics for fixture SQL). `restaurantpro.test.fixture-checkouts=false` turns it off (`TenantBindingTransactionManagerTest`). Production code reads in transactions; a production autocommit read on a listener, job or request thread still fails closed in the suite.
  - The isolation suites are `@StrictTenantScope` (no fallback), with tenants `TenantTestSupport.A` and `B` (PROVISIONING, so jobs of other suites never iterate them) seeded with **identical codes** through `AppRoleSession.tenant(…)` and bound with `TenantTestSupport.inTenant(tenantScopes, tenantId, …)`; an actor of a tenant carries a `TenantContext` as its `Authentication` details. A suite that needs ACTIVE tenants creates its own and closes them after (`ActorlessTenantScopeTest`).
  - The Keycloak Testcontainer (`SharedKeycloak`, pinned 26.x, realms from `deploy/keycloak`) starts only when a suite asks for it (identity and end-to-end, from S72); every other test uses a test JWT (S72).
- Draw per-test ids and keys in `@BeforeEach` or in the test method, never in a field initializer: in module tests one test instance has been seen serving all of a class's methods, so a field-initialized id leaks between them (`81ec2c1`, `TerminalAndVoidTicketsTest`).
- No JUnit `@Nested` test classes. Surefire's plain-text reporter misattributes a class with a nested container (its `.txt` shows 0 tests), which breaks the per-class evidence. Use another top-level class.
- The gate is `cd backend && rtk mvn clean test`: BUILD SUCCESS with 0 failures, 0 errors and **0 skipped**. No `@Disabled`, no assumptions that skip; stream only the cases that apply (`@MethodSource`).
  - The one exception is a QA **expected failure** for a filed bug: a class named `*Repro` (outside Surefire's include patterns, so the gate never discovers it and nothing is skipped), `@Disabled("BUG-NNNN: …")`, run with `rtk mvn test -Dtest=XRepro -Djunit.jupiter.conditions.deactivate=org.junit.*DisabledCondition`. The fix removes `@Disabled` and renames it to `*Test`.
  - Informational measurements (`R2LatencySmoke`, `R3ReportBenchmark`, `R3LoadSmoke`) are also named outside the include patterns and run by name; they fail only on a non-2xx answer. The load smoke against a running stack is `deploy/load/load-smoke.sh` (A56, [deploy/README.md](../../deploy/README.md) "Load smoke").
- **Tests must survive mutation** (R4 review rule): for every rule you add, removing or weakening it in the code must turn at least one test red. Reviewers run mutants (delete the guard, flip a comparison, drop a lock); a guard that no test catches is a finding. Assert the exact coded error and the state after it, not just "some 4xx".
- **System level** (`e2e`): `R1/R2/R3/R4/R5AcceptanceTest` and `RlsAcceptanceTest`/`RlsPermissiveAcceptanceTest` (store isolation, D171) drive the real server over HTTP (`Browser`, CSRF, sessions in PostgreSQL, `TcpFakePrinter`), each on its own empty database (`Installation.FreshDatabase`). `RestartMatrixTest` crashes one instance at a point (a spy throws or parks the request thread) and starts a second application on the same database (`SpringApplicationBuilder`), moving the client there with its cookies (`Browser.movedTo`). Time moves only through `SettlementTestClock`.
- Module tests: `@ApplicationModuleTest(extraIncludes = {"shared", "access", "audit"})` + `@Import(TestcontainersConfiguration.class)`. **Since S46, any module test that boots `orders` also includes `"promotions"`** (orders prices at confirmation through `PromotionsApi`, and loyalty through `LoyaltyApi`), and with it `"customers"`; without it the context does not start. A module test boots only its own module: `shared` holds the `Clock`, JSON, idempotency and notifier beans, `access` holds `AccessPolicy`, `audit` holds `AuditLog`. Add the modules your code calls. A use case that calls `requirePos` also needs a `StoreActivity` bean: include `"organization"` (and create the store), or declare a `@Primary StoreActivity` test bean (see `SseNotificationTest.AllStoresActive`); without one `requirePos` throws `IllegalStateException`.
- Act as a user with `@WithActor(permissions = {...}, storeId = "...")` (`com.xavier.backend.access.WithActor`, test sources): an `ACCOUNT`. Add `employeeId` and `terminalId` for a POS `EMPLOYEE` actor, whose principal id is then the employee id.
- SSE: subscribe with MockMvc (`request().asyncStarted()`), write in a `TransactionTemplate`, and poll the response bytes briefly (notices are sent off the committing thread; Awaitility is not on the classpath).
- Throw-away controllers for HTTP tests are static nested `@RestController`s pulled in with `@Import(Test.Probe.class)`. Spring's test scan skips nested classes of test classes.
- Architecture fixtures live in `com.xavier.archfixture.*`, outside the scanned base package.
